# Ting 0.4.0

Ting receivers now use live, addressable sessions. A WebSocket can receive anonymously after registering accepted apps, or attach one or more Carbon/Silicon identities. Apps can send to every active session for a user or to one specific session. Five-second ping/pong removes lost sessions; reconnecting creates a new session ID.

## Delivery controls

Recipients can choose `allowed`, `silent`, or `blocked` for a sender, application, or notification type. Across matching rules, blocked wins over silent, then allowed. An app may supply `from` to attribute a notification to an account; omitted or null means the app itself. Attribution is asserted by the verified sending app.

Silent tings wait for a daily digest. Ting detects the browser or operating-system time zone and initializes the schedule to **00:00 in that zone**. Without a detected zone it uses **09:00 UTC**, upgrading that provisional default when a zone becomes available. Existing saved schedules and explicit user choices are preserved. The time and IANA time zone are editable, and the digest can be disabled. If no eligible session is active, pending tings wait for a later scheduled run. Pending silent tings and outstanding digest webhook copies are retained until delivery or read handling completes.

Direct session events are live notifications. Account inboxes retain history and local webhooks keep their durable delivery/read acknowledgements. Session-targeted tings never move to a different session.

## Notification definitions

Each type is now exactly `<app-id>.<tingid>`, where `tingid` contains ASCII letters and digits. Operator-configured prefix aliases retain their existing ownership rules. Definitions require a description and a JSON Schema for the `data` object. Authors can update descriptions and schemas; schema changes apply to future sends. Existing idempotent receipts retain their original result.

`GET /v1/apps/{app-id}/types` publicly exposes the definitions and schemas, including credential-free cross-origin reads. Schema references must stay inside the schema document.

## Upgrade existing integrations

Three-part labels remain visible in history but cannot be used for new definitions or sends. Register a replacement two-part type and update producers and type-specific rules:

```sh
ting types register --app dm --type dm.messageReceived \
  --description 'A new message arrived' \
  --schema '{"type":"object","properties":{"message_id":{"type":"string"}},"required":["message_id"]}'
```

Old enabled/disabled preferences migrate to allowed/silent. Required automation delivery still requires recipient opt-in and now respects silent and blocked rules.

The CLI covers anonymous and identified listening, active sessions, sender/app/type preferences, digest schedules, notification schema management, and attributed or session-targeted sends. See the [CLI reference](../../udd/cli.md) and [API contract](../../udd/api.md).
